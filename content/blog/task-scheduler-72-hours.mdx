這個網站跑在我自己的桌機上：Windows 工作排程器開機時啟動 Node.js，Cloudflare Tunnel 把流量轉進來。另外有一支 watchdog 每 5 分鐘檢查一次網站，掛了就自動重啟。

有一天翻 watchdog 的 log，發現它救網站的次數多得不太正常。

## 先看時間

把 watchdog 每次「網站健康檢查失敗」的時間列出來：

```
2026-09-04 17:16
2026-09-07 17:21
2026-09-18 03:16
2026-09-21 03:21
2026-10-07 21:31
2026-10-10 21:36
2026-10-13 21:41
2026-10-18 11:01
2026-10-21 11:06
2026-10-24 11:11
```

兩件事很明顯：

1. 間隔都是 **3 天**
2. 每次都比上一次晚 **5 分鐘**

第二點是關鍵線索。5 分鐘剛好是 watchdog 的檢查間隔：網站在某個時間點死掉，最多 5 分鐘後 watchdog 才發現、把它重啟。如果「死掉」是從啟動那一刻開始倒數 72 小時，那每一輪就會往後推 5 分鐘——時間表完全對得上。中間偶爾斷掉、重新對齊，是因為那幾天有部署，部署會重啟網站，倒數也跟著重來。

還有一個巧合：每次網站掛掉的同一分鐘，GitHub Actions 的 self-hosted runner 也一起掛了。兩個毫不相干的程式同時死，代表問題不在程式本身。

## 第一個猜測：memory leak（錯）

一開始我懷疑是 Next.js 的記憶體洩漏，跑三天把記憶體吃光。所以做了兩件事：

- 把 Next.js 升到當時最新版
- 在自訂 server 裡加一行診斷 log，每 30 分鐘記一次 `process.memoryUsage()`

```
MEM rss=34.3MB heapUsed=32.7MB external=4.3MB arrayBuffers=0.5MB uptime=3.0h
```

結果升級之後照樣三天一掛，而 MEM log 顯示記憶體在掛掉前一路都穩穩的，沒有往上爬。不是洩漏——是程式好好地跑著，然後**瞬間**被終止。

## 真正的凶手

「瞬間被終止」加上「72 小時整」，指向的是外部的東西。用 `schtasks /query /tn kbs0830_NextJS /xml` 把排程工作的設定匯出來看，`<Settings>` 裡**根本沒有** `ExecutionTimeLimit` 這個欄位。

沒寫，就是用預設值：`PT72H`。

在工作排程器的「建立工作」視窗裡，「設定」分頁有一個預設就打勾的選項，英文介面叫「**Stop the task if it runs longer than: 3 days**」（執行超過 3 天就停止工作）。對一次性的批次工作來說這是合理的保險，但對一個要永遠跑下去的網站，就是每三天被強制關掉一次。網站跟 runner 都是我用同樣方式建立的排程工作，所以會一起死。

修法是把上限改成 0（不限制）：

```powershell
$s = New-ScheduledTaskSettingsSet -ExecutionTimeLimit ([TimeSpan]::Zero)
Set-ScheduledTask -TaskName kbs0830_NextJS -Settings $s
```

## 以為修好了，其實沒有

9 月我就照上面那樣改了，在文件裡寫下「已修復」。結果 10 月的 log 照樣 10/07、10/10、10/13 一路掛下去。

再匯出一次 XML：還是沒有 `ExecutionTimeLimit`。最可能的原因是：那次的 `Set-ScheduledTask` 是在**一般權限**的 PowerShell 跑的。我後來用一般權限重跑同一行，確實被拒絕（`PermissionDenied 0x80070005`）——9 月那次大概也是這樣，只是我沒注意到那行紅字，就當作改好了。

最後把所有排程設定寫成一支 `setup-autostart.ps1`，用系統管理員身分跑，跑完再把 XML 撈出來檢查，親眼看到 `<ExecutionTimeLimit>PT0S</ExecutionTimeLimit>` 才算數。

## 附帶損失

每次掛掉，watchdog 最多 5 分鐘就救回來，訪客大概很難碰上。但 Google 的爬蟲會：Search Console 的檢索統計裡，有將近兩成的請求是「伺服器錯誤 (5xx)」——這不全是 72 小時造成的，同一時期還有一次 Tunnel 斷線，但這幾分鐘的空窗肯定有份。對一個靠搜尋被看見的個人網站來說，這比少幾個訪客更傷。

## 學到的事

- **規律的時間比錯誤訊息更有用。** 這次沒有任何 exception 可以看，是把事件時間排在一起，「每 3 天、每次晚 5 分鐘」才露出原因
- **兩個不相干的東西同時壞，先找它們的共同點**，不要分別去修
- **「改好了」要用讀回來的結果證明**，不是用「指令跑完沒報錯」證明——尤其是改到需要權限的系統設定時
- 建排程工作時，那個預設打勾的「3 天」記得取消
